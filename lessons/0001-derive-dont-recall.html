Lesson 1 · The Method

Derive, don’t recall

You already wrote working Run-Length Encoding. So this lesson isn’t about RLE — it’s about the path that could have led you there from a blank editor, with no hints and no snippets. That path is a repeatable method. Learn it here; reuse it forever.

The core idea
Stitching snippets fails on new problems because it skips the thinking and jumps to the typing. The fix is to separate understanding from coding. You solve the problem on paper first — as a human, by hand — and only then translate your hand-method into code. Code is the last step, not the first.

The five steps: UDPCT

This is a lightweight version of George Pólya’s classic framework (primary source below), tuned for coding problems.

  1. Understand Restate the problem in your own words. What are the exact inputs and outputs? Write down 2–3 concrete examples including an empty / edge case.
  2. Do it by hand Solve one example manually, slowly, like a human with a pencil. Narrate every move out loud: “I’m looking at this letter… it’s the same as the last one… so I’ll…” This is the step people skip — and it’s where the whole solution actually lives.
  3. Pattern Watch what your hand kept doing. What did you track? (a running count?) When did you act? (when the character changed?) That repeated behaviour is your algorithm. Write it as plain-English steps — still no code.
  4. Code Now — and only now — translate each plain-English step into a line of code. The typing is mechanical because the thinking is already done.
  5. Test Run your examples from step 1 through the code by hand or in the terminal, edge case first. A mismatch points you at the exact step that was wrong.

Watch it work on RLE

Here is the method applied to the problem you already solved — notice how the code falls out of steps 2–3 almost for free.

1 · Understand

Input: a string. Output: each run of a repeated character replaced by the char + its count.

"aaaabbbccc" → "a4b3c3"
"abc"        → "a1b1c1"   // runs of length 1 still get a count
""           → ""         // edge case

2 · Do it by hand

Reading "aaaabbbccc" left to right, narrating:

“First a. Count is 1. Next is a — same — count 2. Same — 3. Same — 4. Next is b — different! So I write down the run I just finished: a4. Now I’m counting bs, count 1…”

3 · Pattern

What did the hand keep doing? Two behaviours repeated:

  • It kept a running count of the current character.
  • It flushed (wrote char + count, reset count to 1) the moment the character changed.
  • At the very end, the last run is still un-flushed — so flush once more after the loop.

4 · Code

Each bullet becomes a line. This is your code from algorithms/strings/run-length-encoding.ts, now traceable to a reason:

let out = "";
let count = 1;                       // running count (step 3, bullet 1)
for (let i = 1; i < str.length; i++) {
  if (str[i] === str[i - 1]) count++;         // same char → keep counting
  else { out += str[i-1] + count; count = 1; } // changed → flush (bullet 2)
}
out += str[str.length - 1] + count;  // flush the last run (bullet 3)
See it?
The out += str[str.length-1] + count line after the loop — the one that’s easy to forget — isn’t a trick you memorise. It’s just “the last run never got flushed because the loop ran out of characters before the next change.” The hand-trace told you it was needed.
