Lesson 2 · Indexing & Intervals

Off-by-one is a choice, not a guess

You found two binary searches that both work — one uses high = length with <, the other high = length − 1 with <=. It feels like you have to remember which +1/−1 goes where. You don’t. Every one of those symbols is forced by a single decision you make up front. Pick the decision, and the rest is mechanical — pure derive, don’t recall.

The one decision
Before writing a loop over a range, decide: is my range half-open [low, high) or fully-closed [low, high]? That word — whether high is a valid index or one past the end — determines your +1s, −1s, < vs <=, everything. The bugs happen when you mix the two conventions.

What the brackets mean

A range is a pair of bounds. The bracket style is standard maths notation for “is the endpoint included?”

  • [ or ] = closed — the endpoint is part of the range.
  • ( or ) = open — the endpoint is not part of the range; it’s a boundary you stop before.

So for an array of length 5, indices 0..4, the two honest ways to say “the whole thing” are:

index: 0 1 2 3 4 length = 5 [0, 5) ●───●───●───●───●───○ low=0, high=5 ← high is ONE PAST the end low high (half-open) [0, 4] ●───●───●───●───● low=0, high=4 ← high is a REAL index low high (closed)

● = included, ○ = excluded. Notice both describe the same five cells — they just name the right edge differently. That is the whole source of your −1.

The tell
Look at the only two rows that differ: the loop test and the right-half update. In half-open, high = mid (no −1) because high was never a cell you needed to check — it’s the excluded boundary. In closed, high = mid − 1 because high was a real cell, and you just checked mid, so you step one below it. The −1 isn’t a rule — it’s the excluded/included distinction showing up.

Why mixing them is the classic bug

Suppose you wrote closed-style high = length − 1 but half-open-style low < high. Trace [5], searching for 5:

low = 0, high = 0        // length-1 = 0
while (0 < 0)  →  FALSE  // loop never runs!
return false             // ✗ WRONG — 5 is right there

You excluded index 0 by using <, but you named index 0 as a valid cell with length−1. The two halves of your range disagreed about whether high is included. That single-element case is the fastest way to catch a mixed convention — which is exactly your mission’s step 5 (Test the smallest input).

The midpoint: a different axis entirely

Your two versions also compute mid differently. This has nothing to do with intervals — both give the same index. It’s about integer overflow.

FormValue for low=2, high=8Risk
(low + high) / 2 (2 + 8)/2 = 5 low + high can overflow if both are huge (a real bug in Java/C; famously in binary search for ~9 years)
low + (high − low) / 2 2 + (6)/2 = 5 Never overflows — the gap high−low is always ≤ the array size
In JavaScript specifically
JS numbers are 64-bit floats, so you’d need an array of ~4.5 quadrillion elements to actually overflow — it cannot happen in practice here. So both forms are correct in TS/JS. Prefer low + (high − low) / 2 anyway: it’s a habit that stays correct in languages where it matters, and it reads as “start at low, step halfway toward high” — which is what you’re actually doing.

Retrieve — don’t peek

Answer each in your head, then reveal.

Q1. In the half-open convention [low, high), what does high refer to?
One position past the last valid index — an excluded boundary you stop before, never a cell you read.
Q2. Why does closed-style use high = mid − 1 but half-open uses high = mid?
Closed high is an included cell, so after checking mid you must step past it. Half-open high is already excluded, so setting it to mid excludes mid for free.
Q3. What is the single fastest test input to expose a mixed-convention off-by-one?
A one-element array — the boundaries touch immediately, so a wrong < vs <= or a wrong high fails on the first iteration.
Q4. Is (low + high) / 2 ever wrong in TypeScript?
No — it can only overflow above ~4.5 quadrillion elements, impossible in JS. It’s a correctness bug in fixed-int languages, a style choice in TS.
