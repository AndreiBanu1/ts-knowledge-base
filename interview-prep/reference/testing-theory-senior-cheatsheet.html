Testing Principles, Design Techniques & Theory — Senior QA Cheat Sheet

The vocabulary and frameworks a senior is expected to name and apply: the 7 principles, black/white/grey box, the design techniques (equivalence, boundary, decision tables, state, pairwise), test levels & types, the pyramid, and the definitions interviewers use to catch bluffing.

The senior mindset (say this)
Testing reduces risk; it doesn't prove correctness. You can't test everything, so the whole craft is choosing the highest-value tests — driven by risk, using systematic design techniques so coverage is deliberate, not random. "Quality is built in, not tested in."

1 · The 7 principles of testing (ISTQB)

  1. Testing shows the presence of defects, not their absence — passing tests never prove bug-free.
  2. Exhaustive testing is impossible — you can't try every input; use risk + techniques to prioritise.
  3. Early testing saves time and money — shift left; a bug found in design is far cheaper than in prod.
  4. Defects cluster together — a few modules hold most bugs (Pareto). Focus effort there.
  5. Beware the pesticide paradox — the same tests stop finding new bugs; vary and review them.
  6. Testing is context-dependent — you test a banking app differently from a game.
  7. Absence-of-errors is a fallacy — a bug-free product that doesn't meet user needs is still a failure.

2 · Error vs Defect vs Failure (get the chain right)

The causal chain interviewers test
A human makes an Error (mistake) → which introduces a Defect (bug/fault) in the code → which, when executed, may cause a Failure (observable wrong behaviour). Not every defect causes a failure (may be on an unreached path).
Related: Root cause = the underlying reason for the error. A Reliability issue is a pattern of failures over time.

4 · Black-box design techniques (the ones to demo)

Equivalence Partitioning (EP)

Divide inputs into groups that should behave the same; test one value per partition (valid + invalid). Slashes redundant cases.

// Age field valid 18–65:
// Partitions: [<18 invalid] [18–65 valid] [>65 invalid]
// One representative each: e.g. 10, 30, 80

Boundary Value Analysis (BVA)

Bugs cluster at edges. Test the boundaries of each partition: min, min−1, min+1, max, max−1, max+1.

// Age 18–65 → test 17, 18, 19 … 64, 65, 66
// (off-by-one errors live exactly here)

Decision Table

For combinations of conditions → actions. Ensures every rule combo is covered.

Member?>$100?Discount
YY20%

State Transition

For systems with states + events. Test valid transitions and invalid ones.

// Order:
// CREATED →(pay)→ PAID →(ship)→ SHIPPED
// invalid: SHIPPED →(pay)→ ? (should reject)
// Test each arrow + illegal events per state.

Pairwise / Combinatorial

When many parameters each have several values, testing all combinations explodes. Pairwise covers every pair of values — catches most interaction bugs with a fraction of the cases.

Error Guessing (experience-based)

Deliberately throw likely-problem inputs: empty, null, 0, negative, huge, special chars, duplicate submit, expired token.

5 · White-box coverage (know the hierarchy)

CoverageRequiresStrength
StatementEvery line executed onceWeakest
Branch / DecisionEvery if true AND falseStronger (implies statement)
PathEvery independent pathStrongest, often impractical

100% branch coverage ⊃ 100% statement coverage. Coverage is a guide, not a quality guarantee — you can have 100% coverage and still miss the bug.

6 · Test levels & the pyramid

LevelTests
UnitOne function/class in isolation
IntegrationModules/services talking (API, DB)
SystemWhole app end-to-end
AcceptanceMeets business needs (UAT)
// The Test Pyramid (Cohn)
      /\    E2E / UI     ← few, slow, brittle
     /  \   Integration  ← some
    /____\  Unit         ← many, fast, cheap

// Anti-pattern: "ice-cream cone" = mostly
// manual/E2E on top, few unit tests → slow & flaky.
Senior soundbite
"Push tests down the pyramid. Verify logic at the unit/API level where it's fast and stable; reserve slow, flaky E2E for a handful of critical user journeys. The shape of your suite should be a pyramid, not an ice-cream cone."

7 · Test types (functional vs non-functional)

// Functional — WHAT it does
smoke        core paths work? (build sanity)
sanity       narrow check after a small change
regression   old features still work post-change
integration  components work together
acceptance   meets requirements

// Non-functional — HOW WELL it does it
performance  load, stress, spike, soak
security     authz, injection, secrets
usability    ease of use
accessibility a11y / WCAG
compatibility browsers, devices, OS
reliability  behaviour over time
Confusable pairs (common trap)
Smoke = broad + shallow, "is the build stable enough to test?" · Sanity = narrow + deep, "does this specific fix work?" · Verification = "did we build it right?" (reviews, specs) · Validation = "did we build the right thing?" (meets user need) · QA = process/prevention · QC = product/detection · Re-testing = confirm a specific fix · Regression = confirm nothing else broke.

8 · Process, artefacts & lifecycle

// STLC — Software Test Life Cycle
Requirement analysis → Test planning →
Test design (cases) → Environment setup →
Test execution → Closure/reporting

// Bug life cycle
New → Assigned → Open → Fixed →
Retest → Closed  (or Reopened / Rejected /
Deferred / Duplicate / Won't Fix)
// A good bug report
- Title (clear, specific)
- Steps to reproduce (numbered)
- Expected vs Actual result
- Environment (browser/OS/build)
- Severity (impact) & Priority (urgency)
- Evidence: logs, screenshot, trace, video
Severity vs Priority (always asked)
Severity = technical impact of the bug (crash = high). Priority = business urgency to fix it. They're independent: a typo on the homepage logo = low severity, high priority; a crash in a rarely-used admin export = high severity, low priority.

9 · Entry / exit criteria & "done"

// Entry criteria (ready to start testing)
- Requirements/AC available
- Test env + data ready
- Build deployed & smoke passes
// Exit criteria (ready to stop)
- Planned tests executed
- Coverage/pass-rate target met
- No open critical/high defects
- Risks documented & accepted

DoR (Definition of Ready) — a story is testable: clear AC, no blockers. DoD (Definition of Done) — coded, reviewed, tested, automated, merged. Know both for agile/scrum questions.

10 · Shift-left, agile & automation strategy

  • Shift-left: test earlier — review requirements, write tests alongside code, run in CI on every PR.
  • Automate the right things: stable, repetitive, high-value regression paths. Don't automate one-offs, rapidly-changing UI, or exploratory work.
  • Manual still matters: exploratory, usability, and new features benefit from a human. Automation checks known behaviour; exploration finds the unknown.
  • ROI: automation costs upfront, pays off over many runs. Justify it by execution frequency × stability × risk.
