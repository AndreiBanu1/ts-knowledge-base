TypeScript / JS Fundamentals — Senior QA Cheat Sheet

The language questions that show up in QA interviews: scoping, hoisting, closures, async, value-vs-reference, collections, OOP, and the two design patterns you'll be asked about (Singleton, Factory) — each tied to where it lives in a test framework.

The mental model that ties it together
JS is single-threaded with an event loop. Objects/arrays are handled by reference, primitives by value. async/await is just sugar over Promises. Almost every "gotcha" question is one of these three ideas in disguise.

1 · var / let / const & hoisting

ScopeHoisted?Reassign?
varfunctionYes → undefinedYes
letblock { }Yes, but TDZ*Yes
constblock { }Yes, but TDZ*No (binding)

*TDZ = Temporal Dead Zone: the variable exists but touching it before its declaration throws ReferenceError.

// Hoisting: declarations move up, assignments don't
console.log(a); // undefined  (var hoisted)
var a = 1;

console.log(b); // ReferenceError (TDZ)
let b = 2;

// function declarations are fully hoisted
foo();          // works
function foo() {}
// function EXPRESSIONS are not
bar();          // TypeError
const bar = () => {};
// const ≠ immutable — only the BINDING is fixed
const arr = [1, 2];
arr.push(3);     // ✅ allowed (contents mutable)
arr = [];        // ❌ TypeError (rebinding)

// Object.freeze for shallow immutability
const cfg = Object.freeze({ retries: 2 });
cfg.retries = 5; // silently ignored (throws in strict)

// Rule: default to const, use let when you must
// reassign, never use var.
Classic interview trap
// var in a loop — all callbacks share ONE i
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 3 3 3
// let creates a NEW binding each iteration
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 0 1 2
This is a closure + scope question — see §3.

2 · Pass by value vs by reference

The rule
Primitives (number, string, boolean, null, undefined, symbol, bigint) are copied by value. Objects, arrays, functions are copied by reference (the reference itself is passed by value — you copy the "address", not the box). 
// Primitive — copy
let a = 1; let b = a; b++;
// a=1, b=2 (independent)

// Object — same box
const o1 = { n: 1 };
const o2 = o1;
o2.n = 99;        // o1.n is now 99 too!

function mutate(o) { o.n = 0; }
mutate(o1);       // o1.n === 0 (caller affected)
// Why it matters in tests: shared test data leaks
const baseUser = { role: 'admin' };
function makeUser(over) {
  return { ...baseUser, ...over }; // shallow copy!
}
// Deep structures need a deep clone:
const copy = structuredClone(baseUser);

// === on objects compares REFERENCES, not contents
{a:1} === {a:1}   // false
[1] === [1]       // false

3 · Closures

A closure = a function that remembers the variables from the scope where it was defined, even after that scope has returned. It's how JS does private state.

function counter() {
  let count = 0;              // "private"
  return () => ++count;      // closes over count
}
const next = counter();
next(); // 1
next(); // 2  — count persists, but is inaccessible

// In test frameworks: factory that captures config
function apiClient(baseURL) {
  return {
    get: (path) => fetch(baseURL + path),
  };
} // baseURL is "remembered" — no need to repass it
const api = apiClient('https://app.test');
Where it shows up in automation
Custom fixtures, retry wrappers, and "builder" test-data helpers all rely on closures to capture state (a token, a base URL, a page) without exposing it globally.

4 · Promises, async/await, the event loop

// A Promise: pending → fulfilled | rejected
const p = new Promise((resolve, reject) => {
  ok ? resolve(value) : reject(err);
});

// Consume with .then/.catch OR async/await
p.then(v => ...).catch(e => ...).finally(...);

async function run() {
  try {
    const v = await p;      // unwraps the promise
  } catch (e) { /* handles reject */ }
}
// Run in parallel vs series — big perf point
// SERIES (slow): each awaits the previous
const a = await f(); const b = await g();

// PARALLEL (fast): start both, then await
const [a2, b2] = await Promise.all([f(), g()]);

// Promise combinators
Promise.all([...])        // all succeed, or reject fast
Promise.allSettled([...]) // wait all, never rejects
Promise.race([...])       // first to settle
Promise.any([...])        // first to FULFILL
Traps interviewers love
// 1. Forgetting await → test passes before assert runs (flaky!)
expect(page.getByText('x')).toBeVisible();       // ❌ missing await
await expect(page.getByText('x')).toBeVisible(); // ✅

// 2. await in a loop = serial. Map to promises + Promise.all for parallel.
for (const id of ids) await del(id);             // slow, serial
await Promise.all(ids.map(id => del(id)));       // parallel

// 3. Microtasks (promises) run before macrotasks (setTimeout)
console.log(1);
setTimeout(() => console.log(4));
Promise.resolve().then(() => console.log(3));
console.log(2);            // prints 1 2 3 4

7 · Design patterns — Singleton & Factory

// SINGLETON — one shared instance app-wide.
// Use for: a single API client, DB connection,
// config, or logger shared across tests.
class ApiClient {
  private static instance: ApiClient;
  private constructor(public baseURL: string) {}
  static get(url = 'https://app.test') {
    if (!ApiClient.instance)
      ApiClient.instance = new ApiClient(url);
    return ApiClient.instance;
  }
}
const a = ApiClient.get();
const b = ApiClient.get(); // a === b (same instance)
// FACTORY — a function/class that decides WHICH
// object to build. Use for: test-data builders,
// picking a page object by name, browser setup.
type Role = 'admin' | 'guest';
function makeUser(role: Role) {
  const base = { name: 'Test', createdAt: 0 };
  switch (role) {
    case 'admin': return { ...base, perms: ['*'] };
    case 'guest': return { ...base, perms: [] };
  }
}
const admin = makeUser('admin');
// Factory centralises creation → change shape once.
Interview soundbites
Singleton: "One instance, global access point — I'd use it for a shared API client or config so every test hits the same configured object. Downside: it's global state, which can hurt test isolation, so I keep it stateless or immutable."

Factory: "Encapsulates object creation so callers don't hard-code construction. In automation it's my test-data builder — makeUser('admin') — so when the user shape changes I fix one place, not fifty tests."
