API / HTTP / GraphQL / DB — Senior QA Cheat Sheet

What a Senior QA is expected to know about the layer under the UI: HTTP methods & status codes, REST vs GraphQL, network concepts, and enough database literacy to seed/verify state.

Why QA tests the API layer
API tests are faster, more stable, and closer to the logic than E2E. Seniors push testing down the pyramid: validate business rules via API, seed test state via API/DB, and reserve slow UI E2E for critical journeys.

1 · HTTP methods (verbs)

MethodPurposeSafe?Idempotent?
GETRead a resourceYesYes
POSTCreate / trigger actionNoNo
PUTReplace a resource wholesaleNoYes
PATCHPartially updateNoNo*
DELETERemove a resourceNoYes
HEADLike GET, headers onlyYesYes
OPTIONSDiscover allowed methods (CORS preflight)YesYes

Safe = no server state change. Idempotent = calling N times = calling once. *PATCH can be idempotent depending on the payload. These two terms are a very common interview question.

The 401 vs 403 gotcha
401 Unauthorized = "I don't know who you are" (missing/bad credentials). 403 Forbidden = "I know who you are, but you can't do this." Naming them correctly is a senior signal.

3 · Anatomy of a request/response

// Request
POST /api/users HTTP/1.1
Host: app.test
Content-Type: application/json      ← body format
Authorization: Bearer <token>        ← auth
Accept: application/json            ← want back

{ "name": "Ada" }                    ← body
// Response
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/users/42             ← new resource
Set-Cookie: session=...; HttpOnly

{ "id": 42, "name": "Ada" }

Headers a QA cares about: Content-Type, Authorization, Accept, Cache-Control, Set-Cookie, Location, X-Request-Id (tracing). Auth styles: Bearer/JWT token, API key, Basic (base64 user:pass), OAuth2, session cookie.

4 · REST vs GraphQL

RESTGraphQL
EndpointsMany (/users, /users/1/orders)One (/graphql)
Data shapeServer decides; fixed per endpointClient asks for exactly the fields it needs
Over/under-fetchingCommon problemSolved — you get only what you query
Method/verbGET/POST/PUT/DELETE map to CRUDAlmost always POST; op type in body
Status codesRich (404, 201, ...)Often 200 even on errors — check errors[] in body!
Operations—query (read), mutation (write), subscription (live)
// GraphQL query — ask for exact fields
query {
  user(id: 1) {
    name
    orders { id total }
  }
}
// Testing GraphQL = POST to one endpoint
await request.post('/graphql', {
  data: { query: '{ user(id:1){ name } }' },
});
// ⚠️ assert on body.errors, not just status 200!

HTTP request/response

// Terms to have ready
CORS      cross-origin rules; preflight OPTIONS
Cookie    server state in the browser (HttpOnly, Secure)
Cache     Cache-Control, ETag, 304 Not Modified
CDN       edge caching of static assets
Latency   round-trip time; Throughput = volume
Idempotency-Key  safe retries for POST
  • HTTP vs HTTPS: HTTPS = HTTP over TLS (encrypted, authenticated). Always expected in prod.
  • Stateless: HTTP itself keeps no memory between requests — state is carried by cookies/tokens each time.
  • Synchronous vs async APIs: some POSTs return 202 Accepted and do work later (polling/webhooks) — test the eventual state, not just the ack.

6 · Database concepts for QA

// SQL you should be able to write cold
SELECT name, email FROM users
WHERE role = 'admin'
ORDER BY created_at DESC
LIMIT 10;

INSERT INTO users (name) VALUES ('Ada');
UPDATE users SET role = 'admin' WHERE id = 42;
DELETE FROM users WHERE id = 42;

-- join two tables
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id;
// Concepts
Primary key   unique row id
Foreign key   ref to another table's PK
Index         speeds lookups (cost on writes)
Transaction   all-or-nothing (COMMIT/ROLLBACK)
JOIN types    INNER / LEFT / RIGHT / FULL
Normalization reduce duplication across tables
SQL (relational)NoSQL (e.g. Mongo)
ShapeTables, rows, fixed schemaDocuments/KV, flexible schema
GuaranteesACID, strong consistencyOften BASE, eventual consistency
Use forRelations, transactionsScale, flexible/varied data
ACID (one-liners)
Atomicity (all-or-nothing) · Consistency (valid state → valid state) · Isolation (concurrent txns don't corrupt) · Durability (committed = survives crash).

7 · How this shows up in test automation

TaskApproach
Seed test dataPOST via API or INSERT via DB before the test — faster + more reliable than clicking through the UI.
Verify a side effectAfter a UI action, assert the API/DB actually changed (don't trust the UI alone).
Clean upDELETE created records in teardown (fixtures) so tests stay isolated.
Auth setupHit the login/token endpoint once, reuse the token/storageState across tests.
Contract/schema checksAssert response status, body schema, and required fields — catches breaking API changes early.
Negative testingSend bad/empty/oversized payloads; assert 400/401/403/422, not 500.
// Playwright API test — the pattern to reproduce in the interview
test('create user returns 201 with id', async ({ request }) => {
  const res = await request.post('/api/users', { data: { name: 'Ada' } });
  expect(res.status()).toBe(201);
  const body = await res.json();
  expect(body).toMatchObject({ name: 'Ada' });   // schema/contract
  expect(body.id).toBeGreaterThan(0);
});
