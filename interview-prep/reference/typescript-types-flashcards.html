The 4 must-knows (if nothing else)
1. Generic getter <T, K extends keyof T>(o: T, k: K): T[K] · 2. Utility types Partial / Pick / Omit / Record · 3. ?? vs || (null-ish vs all-falsy) · 4. Narrowing with typeof / control-flow.

Generics most asked

Q1. Write a fully type-safe getProp(obj, key) so the return type tracks the key (no casting).
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
getProp({ name: 'Ada', age: 30 }, 'name'); // typed string
getProp({ name: 'Ada' }, 'nope');          // ❌ compile error
Say it: "K extends keyof T = key must be a real key of T; T[K] = the type of that property, so the return tracks the key."
Q2. What does <T> mean, and why use a generic instead of any?
<T> is a type parameter — a placeholder the caller fills in. Unlike any, it preserves the relationship between input and output types, so you keep full type-checking. 
function first<T>(arr: T[]): T | undefined { return arr[0]; }
first([1, 2]);       // number | undefined
first(['a', 'b']);   // string | undefined
Q3. Constrain a generic so it only accepts things with an id: number.
function save<T extends { id: number }>(entity: T): T {
  return entity;
}
extends here = "T must be at least this shape." This is a generic constraint.

Utility types memorize

Q4. One line each: Partial<T>, Required<T>, Readonly<T>.
Partial<T> — all properties optional. · Required<T> — all properties mandatory. · Readonly<T> — all properties immutable (no reassignment).
Q5. Pick<T, K> vs Omit<T, K> — what does each produce?
Pick<T, K> — keep only the listed keys.
Omit<T, K> — keep everything except the listed keys. 
type Card = Pick<User, 'id' | 'name'>;   // just id + name
type Safe = Omit<User, 'password'>;      // all but password
Q6. What is Record<K, V>? Give an example.
An object type with keys of type K and values of type V. 
const counts: Record<string, number> = { a: 1, b: 2 };
type Roles = Record<'admin' | 'guest', boolean>;
Q7. QA use How does Partial<T> help a test-data builder?
Lets a factory accept only the fields you want to override; the rest come from a default. 
function makeUser(overrides: Partial<User> = {}): User {
  return { id: 1, name: 'Test', role: 'guest', ...overrides };
}
makeUser({ role: 'admin' }); // only override what matters

?? vs || common trap

Q8. What's the difference between || and ?? for defaults?
|| falls back on any falsy value: 0, '', false, NaN, null, undefined.
?? falls back only on null or undefined.
Q9. Predict each: 0 || 100 · 0 ?? 100 · '' || 'x' · null ?? 'x'.
0  || 100     // 100  (0 is falsy)
0  ?? 100     // 0    (0 is a real value)  ← the key case
'' || 'x'     // 'x'  ('' is falsy)
null ?? 'x'   // 'x'  (null triggers ??)
Soundbite: "const port = cfg.port ?? 8080 — with ||, a real port: 0 would be wrongly overwritten."
Q10. What does ?. (optional chaining) do, and what does it return when it short-circuits?
Safely accesses a nested property; if any link is null/undefined it stops and returns undefined instead of throwing. 
user?.profile?.name  // undefined if user or profile is null/undefined
Pairs naturally with ??: user?.name ?? 'Anonymous'.

Narrowing & special types reasoning

Q11. Inside and after the guard, what type is x? Why does it compile? 
function len(x: string | string[]) {
  if (typeof x === 'string') return x.length;
  return x.length;
}
Inside the if: x is string (typeof guard). After it: x is string[] — TS knows a string would already have returned (control-flow narrowing). Compiles because both have .length.
Q12. Why won't this compile, and how do you fix it type-safely? 
function up(x: unknown) { return x.toUpperCase(); }
unknown must be narrowed before use — that's its whole point over any. 
function up(x: unknown) {
  if (typeof x === 'string') return x.toUpperCase();
  throw new Error('not a string');
}
A union like string | unknown does not fix it — x is still unknown.
Q13. unknown vs any — one sentence.
Both hold any value, but unknown is type-safe — you must narrow it before using it; any disables all type-checking. Prefer unknown.
Q14. interface vs type — when each?
interface — object shapes; can be extended and merges declarations; the convention for objects/classes.
type — can do things interface can't: unions, tuples, primitives/aliases (type Status = 'pass' | 'fail'). Lead with the union point — it's the real differentiator.
Q15. What are as and ! (e.g. x!), and what's the risk?
as = type assertion ("trust me, it's this type"). x! = non-null assertion ("this isn't null/undefined"). Both are escape hatches — they silence the compiler without runtime checks, so a wrong assertion becomes a runtime crash. Prefer narrowing.
Q16. bonus What's a discriminated union and why is it nice for narrowing?
A union of object types sharing a literal "tag" field; switching on the tag narrows the type automatically. 
type Result =
  | { status: 'ok';   data: string }
  | { status: 'error'; message: string };
if (r.status === 'ok') r.data;      // narrowed
else                   r.message;   // narrowed
