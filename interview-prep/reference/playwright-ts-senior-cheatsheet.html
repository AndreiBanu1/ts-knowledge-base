Playwright + TypeScript — Senior QA Cheat Sheet

Everything high-yield for a Senior QA Automation interview, on one printable sheet. Skim it tonight, keep it open tomorrow. Grouped as: Locators → Assertions → Waiting → Fixtures/POM → Network → Config/CI → TS-for-QA → Senior talking points.

The one idea that signals "senior"
Playwright's whole design is web-first, auto-waiting assertions on resilient locators. Juniors add waitForTimeout and use CSS/XPath; seniors use role/label locators, lean on auto-waiting, and never sleep. If you internalise one thing, make it this.

1 · Locators — prefer user-facing, avoid brittle

A Locator is lazy: it doesn't find the element until you act/assert on it, so it re-queries the DOM every time — that's what makes it resilient to re-renders.

PriorityLocatorUse for
1getByRole('button', { name: 'Submit' })Almost everything. Mirrors accessibility tree.
2getByLabel('Email')Form fields (label association).
3getByPlaceholder / getByText / getByAltText / getByTitleWhen no role/label fits.
4getByTestId('cart-total')Dynamic content, no stable a11y handle.
lastpage.locator('.css') / XPathEscape hatch only. Brittle.
// Chaining & filtering (very senior-friendly)
page.getByRole('listitem')
    .filter({ hasText: 'Product 2' })
    .getByRole('button', { name: 'Add' });

// Nth / first / last
page.getByRole('listitem').first();
page.getByRole('listitem').nth(2);

// Scope within a parent
const row = page.getByRole('row', { name: 'Order 5' });
await row.getByRole('button', { name: 'Cancel' }).click();
// Strictness: locators are STRICT by default —
// if 2+ match, the action throws. That's a feature.

// Relative / layout locators
page.getByRole('button').and(page.getByTitle('Sub'));
page.getByText('Price').locator('..'); // parent (XPath)

// Test-id attribute is configurable in config:
// use: { testIdAttribute: 'data-qa' }

2 · Assertions — web-first (auto-retrying) vs generic

The #1 flakiness fix
Web-first assertions auto-retry until they pass or time out. await expect(locator).toBeVisible() keeps re-checking. expect(await locator.isVisible()).toBe(true) checks once — flaky. Always await expect(locator)…, never assert on an already-resolved boolean. 
// Web-first (retrying) — await the whole expect
await expect(page.getByText('Welcome')).toBeVisible();
await expect(locator).toHaveText('Done');
await expect(locator).toHaveValue('abc');
await expect(locator).toHaveCount(3);
await expect(locator).toBeEnabled();
await expect(locator).toBeChecked();
await expect(page).toHaveURL(/dashboard/);
await expect(page).toHaveTitle('Home');
await expect(locator).toHaveAttribute('href', '/x');
// Generic (NO retry) — value already resolved
expect(1 + 1).toBe(2);
expect(arr).toContain('x');
expect(obj).toEqual({ a: 1 });

// soft — collect failures, don't stop the test
await expect.soft(loc).toHaveText('a');
await expect.soft(loc2).toBeVisible();

// custom timeout per assertion
await expect(loc).toBeVisible({ timeout: 10_000 });

3 · Auto-waiting — why you never sleep

Before every action, Playwright runs actionability checks: the element must be attached, visible, stable (not animating), receives events (not obscured), and enabled. It waits for all of these automatically, up to the timeout.

// ✅ These already wait — no sleep needed
await page.getByRole('button').click();
await page.getByLabel('Email').fill('a@b.com');

// ✅ Wait for a condition/event explicitly
await page.waitForLoadState('networkidle');
await page.waitForURL('**/dashboard');
await expect(locator).toBeVisible(); // preferred
// ❌ The anti-pattern that flags you as junior
await page.waitForTimeout(3000); // arbitrary sleep

// Waiting for a response as part of an action:
const [resp] = await Promise.all([
  page.waitForResponse('**/api/cart'),
  page.getByRole('button', { name: 'Add' }).click(),
]);

4 · Fixtures & Page Object Model

Fixtures = Playwright's dependency injection: set up/tear down state per test, on demand, in isolation. POM = encapsulate page structure + actions in a class so tests read as intent.

// Page Object
export class LoginPage {
  constructor(private page: Page) {}
  get email() { return this.page.getByLabel('Email'); }
  get pw()    { return this.page.getByLabel('Password'); }
  async goto() { await this.page.goto('/login'); }
  async login(e: string, p: string) {
    await this.email.fill(e);
    await this.pw.fill(p);
    await this.page.getByRole('button',
      { name: 'Sign in' }).click();
  }
}
// Custom fixture that provides the page object
import { test as base } from '@playwright/test';

type Fixtures = { loginPage: LoginPage };

export const test = base.extend<Fixtures>({
  loginPage: async ({ page }, use) => {
    const lp = new LoginPage(page);
    await lp.goto();
    await use(lp);          // test runs here
    // teardown after use()
  },
});
// test('...', async ({ loginPage }) => { ... })
Senior nuance
test.beforeEach vs fixtures: fixtures compose, run only when a test requests them, and tear down automatically — prefer them for shared setup. Use storageState to log in once and reuse auth across tests (huge speed win) — see Config.

5 · Network — mocking, intercepting, API testing

// Mock/stub a response
await page.route('**/api/users', route =>
  route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([{ id: 1, name: 'A' }]),
  }));

// Block resources (speed, isolation)
await page.route('**/*.{png,jpg}', r => r.abort());

// Modify a real response
await page.route('**/api/x', async route => {
  const resp = await route.fetch();
  const json = await resp.json();
  json.role = 'admin';
  await route.fulfill({ response: resp, json });
});
// Pure API testing via request fixture
test('api', async ({ request }) => {
  const res = await request.post('/api/users', {
    data: { name: 'A' },
  });
  expect(res.status()).toBe(201);
  expect(await res.json())
    .toMatchObject({ name: 'A' });
});

// Assert a request fired
const req = page.waitForRequest('**/track');
await page.getByRole('button').click();
await req;

7 · TypeScript for QA — what gets probed

// async/await + typing a return
async function getUser(id: number): Promise<User> {
  const r = await fetch(`/u/${id}`);
  return r.json() as Promise<User>;
}

// interface vs type
interface User { id: number; name: string; }
type Status = 'pass' | 'fail' | 'skip'; // union

// generics — reusable, type-safe helper
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

// optional / readonly / partial
interface Opts { retries?: number; }
function run(o: Readonly<Opts>) {}
type Draft = Partial<User>;
// Utility types worth naming
Partial<T> Required<T> Readonly<T>
Pick<T,K> Omit<T,K> Record<K,V>

// unknown vs any
let x: unknown;        // must narrow before use
if (typeof x === 'string') x.toUpperCase();

// ?? vs ||  and  ?.  optional chaining
const port = cfg.port ?? 8080; // only null/undef
const name = user?.profile?.name;

// Promise.all — run in parallel, await together
const [a, b] = await Promise.all([f(), g()]);

8 · Senior talking points — say these out loud

They askStrong answer (compressed)
How do you deal with flaky tests?Root-cause, don't retry-mask. Common causes: arbitrary sleeps → use web-first assertions; racing network → waitForResponse/mocking; shared state → isolate via fixtures; animations → auto-wait handles stability. Use trace: 'on-first-retry' to diagnose. Retries hide, they don't fix.
Why Playwright over Selenium/Cypress?Auto-waiting + web-first assertions cut flakiness; real cross-browser (Chromium/Firefox/WebKit); runs out-of-process so no in-page limits (multi-tab, multi-origin, iframes); fast parallelism; built-in trace viewer, network mocking, API testing. Cypron runs in-browser (limits multi-tab/origin).
What makes a good test suite?Fast, isolated (no inter-test deps), deterministic, readable (POM = intent), right level of the pyramid (mostly unit/API, fewer E2E), tests behaviour not implementation, resilient locators, runs in CI on every PR.
Test pyramid / strategy?Many unit, some integration/API, few E2E. Push logic checks down to fast layers; reserve E2E for critical user journeys (login, checkout). E2E is expensive + slow — be selective.
Page Object Model — why?Single source of truth for selectors/actions; tests express what not how; change UI → fix one class. Keep assertions in tests, not in POs (POs model the page, not expectations).
How do you test an API?Playwright's request fixture or a setup project — validate status, schema/body, headers, auth, error cases. Fast, stable, great for seeding state before E2E.
Auth without logging in every test?Global setup logs in once, saves storageState (cookies+localStorage) to a file; reuse via use: { storageState }. Tests start authenticated → faster + less flaky.
How do you keep tests maintainable at scale?POM + fixtures for reuse, test-ids where a11y locators don't fit, tagging (@smoke/@regression), parallelism + sharding in CI, code review of tests like prod code, no hard sleeps ever.
Live-coding survival kit
Think out loud (they grade reasoning, not just the answer). Use your UDPCT method: restate the task, name inputs/outputs, do a tiny trace, state the plan in plain English, then code. Scaffold: test('...', async ({ page }) => { await page.goto(); /* arrange */ /* act */ /* assert */ });. Reach for getByRole first, await expect(...) for every check, and narrate why each choice resists flakiness.
